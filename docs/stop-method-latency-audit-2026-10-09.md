## 新证据：延迟集中在停止请求

以同一 stream 0 的 `stop_move` 完整请求 frame 1269 和完整回复 frame 1333 为窗口，其间新发出的 **24 次只读 RPC 全部在停止回复之前完成**：

| 方法 | 次数 | 完整消息往返范围 / ms |
| --- | ---: | ---: |
| get_robot_state | 5 | 1.862～3.876 |
| get_estop_reason | 5 | 1.222～10.772 |
| get_kin_data | 5 | 1.389～11.251 |
| get_tcp | 3 | 1.400～2.798 |
| get_claw | 3 | 1.514～2.582 |
| get_running_motion | 3 | 1.251～6.151 |

这些均来自同一抓包时间基准，不涉及应用时钟对齐。与停止请求的 613.042 ms 相比，连接仍在持续完成其他请求。这削弱了“整条连接断续约 600 ms”及“SDK 将所有回复串行阻塞在停止调用之后”的解释；不能排除停止回复单独延迟，也不能据此确定控制器内部执行顺序。

frame 1271 出现覆盖停止请求 TCP 字节范围的对端 ACK：相距 2.236 ms，ACK 61704，停止请求 nextseq 61631。**TCP 字节被确认不等于控制器应用已接受或执行停止。** 本机捕获点不能定位控制器方法入口。

离线 TShark 对该完整 stream 检查 retransmission、lost_segment、out_of_order、zero_window、duplicate_ack，均无匹配帧。未见这些标志不证明无线网络无丢包、无延迟或捕获无遗漏；本报告不以此排除网络因素。

## 收窄后的排查顺序

另一个直接影响 VR 响应的风险是发点间隔：本次 25 个 PVAT 的日志时域均为 80 ms，但同流完整请求的 24 个相邻间隔有 **11 个超过 80 ms**，最长 **100.390 ms**。粗粒度应用 monotonic 仅识别出 4 个超限间隔，不能替代抓包的同源时间统计。IK 完整消息往返为 3.410～24.453 ms，中位数 8.642 ms。

对照官方 PVAT 说明，这提示发点连续性存在自动减速风险，可作为平移响应差的后续离线优化依据。这里测量的是本机请求完整出现的间隔，并非控制器实际接收间隔；尚不能证明发生了自动减速，也不能仅凭此解释全部位移损失。不会为掩盖间隔问题直接增大时域或速度。

1. **先取得既有控制器证据。** 核对本次现场软件/固件版本，以及若已存在的控制器诊断日志：停止方法收到请求、执行停止、发回 id 547 回复的时刻。当前没有这些控制器内部材料，不能将等待拆成“控制器处理”和“回复传输”。机器人的应用日志时间也不能未经校准与本机抓包直接相减。
2. **优先检验方法本身的等待语义。** 待证假设包括运动停止处理/减速阶段才返回，或运动队列使停止方法等待。现有数据不证明任一假设。单纯换 Python await、缩小本机锁或加大 timeout，均缺乏针对性证据。
3. **下一次动作只能做单变量比较。** 若必须再采集，先准备与本次相同的低速范围和捕获身份，只选择一个能区分上述假设的变量；需要新的用户明确授权与现场条件。尚未启动或批准该比较，不重复同一诊断碰碰运气。

目前不改变 PVAT、200 ms 门限、`stop_unverified`、停止升级或自动恢复规则。连续 VR 控制仍受运动停止验收阻挡，物理仿真后续处理。
