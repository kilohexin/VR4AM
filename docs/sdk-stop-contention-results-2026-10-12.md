## 要回答的问题

此前同一 native SDK 的立即回环回复较快，延迟停止期间只检查了少量串行状态读取。本轮进一步检查：**24 条读取已经到达模拟服务端、尚未回复时，SDK 能否完成立即停止回复；停止延迟时，完整状态读取能否先完成。**

这不是生产 adapter 锁排队、SDK 发送队列积压或 PVAT 运动负载的重现。服务端屏障明确要求读取已发送完毕。本轮不修改生产停止逻辑或配置。

## 实验与约束

新增 `scripts/sdk_stop_contention_probe.py`，复用现有已审查回环服务和连接限制：只建自有 `127.0.0.1` 随机端口，没有目标 IP 或配置参数，不读取现场配置、不发现设备。服务端固定允许空参数 `stop_move` 和六种状态读取，拒绝 PVAT、夹爪写入、Home、复位及 `stop_sys`。

使用安装的 `lebai-sdk-asyncio 0.3.13`；二进制 SHA-256 为 `ad2a68619b25d627593bd5f13f83f17784e7a2c10aa9615db8bd1b681f9fd03b`，与此前现场 SDK 一致，若不一致则在初始化前拒绝运行。

六种读取为 robot state、estop reason、kin data、TCP、claw、running motion，每种 4 条。模拟器将读取回复挂起，确认全部已到达后才发送一次停止；分别注入停止回复 0/600 ms、读取回复 0/100 ms，并补 RPC 错误分支。所有状态、关节、TCP、夹爪均为合成常量。

记录同进程 `perf_counter_ns` 的 SDK 调用开始、模拟端请求到达、回复发送开始和 SDK 返回。请求的 sleep 时长不是实测下限，Windows 调度可能令实测略短或略长。不能把这些时间与历史抓包或控制器时钟直接相减。

## 最终结果

最终源码独立执行两轮，每轮 7 个条件各重复 3 次，共 **42 次**；以下为每条件合计 6 次的 SDK await 范围：

| 条件 | SDK await，ms | 在停止完成前返回的读取数 |
| --- | ---: | --- |
| 立即停止，无读取 | 0.80–1.07 | 0 |
| 立即停止，24 条立即读取回复 | 1.37–2.59 | 1 或 2 |
| 立即停止，24 条读取回复延迟 100 ms | 0.57–1.78 | 0 |
| 停止回复请求延迟 600 ms，无读取 | 594.15–616.56 | 0 |
| 停止回复请求延迟 600 ms，24 条立即读取回复 | 594.92–618.19 | 全部 24 |
| 停止回复请求延迟 600 ms，24 条读取回复延迟 100 ms | 596.08–620.08 | 全部 24 |
| 立即 RPC 错误，24 条读取回复延迟 100 ms | 0.65–1.09 | 0，错误正确传递 |

所有条件的模拟停止回复发送开始至 SDK 完成间隔不超过 **1.47 ms**。42 次均只有 1 个停止请求、准确的读取数量、成功关闭本机连接。六类 SDK 返回值均与固定 fixture 核对，包括 SDK 对 Cartesian 和夹爪默认字段的转换。

服务端回显各请求 ID 并拒绝重复 ID；SDK 按方法返回正确 fixture。但同一种方法的四次读取使用相同值，因此不能证明这些同方法请求各自独立的数据关联。

结论限定于所测条件：24 条已经发送、尚未收到回复的完整状态读取没有引入约 600 ms 的停止等待。模拟器主动延迟停止回复时，SDK 仍能先完成所有读取。此结果不能排除真实 PVAT、不同负载、SDK 其它条件路径、Wi-Fi 或控制器处理造成延迟。

## 真机主线的缺口

现场约 **613.042 ms** 的完整停止请求至回复仍未归因，物理停止在 200 ms 内没有得到确认。现有证据缺少控制器的方法入口、停止执行及回复发送时刻。

下一步需要控制器既有内部日志，或原厂对当前 RC 版本停止回复阶段、日志读取入口和受支持停止确认方法的说明。现有[原厂问题稿](vendor-stop-latency-questions-2026-10-10.md)尚未发送。单纯重复相同运动不能补出这些内部边界。

100 ms 输入有效期、200 ms 停止 RPC 期限、停止失败锁存及不自动升级/重试/复位/Home 保持。没有机器人或 L Master 访问，没有现场动作、配置/抓包修改或对外消息。持续真机 VR 与真实 Trigger 抓取仍未验收。
