# 停止事务生产集成：离线验证记录

## 范围与现场边界

本轮把已讨论的请求所有权原型接入生产适配器。只做本机离线开发及假 SDK 测试，未连接机械臂、未修改现场配置、不联系厂商。本文不是实验室运动放行单。

历史停止后约 16–22 mm 的位置变化、启动抖动及真实 SDK/控制盒行为仍未定位完毕。软件测试通过不能证明这些真机异常已消除。

## 已实现的行为

- 同一次运动的 Grip 松开、Stop、shutdown/disconnect 共用停止事务。每个事务中 `stop_move`、`stop_sys` 各最多首次发送一次；重复调用复用原请求及截止时间。
- 保留首轮 200 ms RPC 等待、500 ms 停止验证预算和首次系统停止升级条件，不延长预算、不放宽限位。
- 停止 RPC 由独立任务持有。调用方超时/取消不伪装成远端取消；迟到返回、迟到异常、退出时未决请求保留诊断，不清除原故障。
- RPC 返回与静止确认分开。重复停止不会重置静止验证期限；已确认后发生位置变化仍要重新判定，不能靠旧成功直接放行。
- 断连接管与停止串行化，防止关闭之后再创建系统停止请求。断连期间拒绝运动和重连；新连接不复用旧连接请求。
- 新运动只有在旧停止事务无未决请求、无故障时才开启新的运动周期。

首轮 `stop_move` 与 `stop_sys` 仍可能重叠：不能因等待未返回的前者而无限阻塞既有升级。这次去重不等于证实系统失能路径安全，也不等于解释了现场漂移。

## 本轮发现并修复的应用退出回归

严格保留取消后的未知结果后，全量测试暴露网页关闭时的停止失败。发现两条本地取消路径：控制循环退出会取消正在停止的任务；WebSocket 外层取消域会打断断连清理。

分别添加回归测试，先观察失败再修复：控制循环给已进入停止的任务有界收尾机会；WebSocket 断连清理隔离外层取消，仍使用后端原有超时判据。没有通过恢复“取消后清除故障”来隐藏失败。
