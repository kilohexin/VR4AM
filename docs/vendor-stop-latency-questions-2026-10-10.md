# 乐白技术支持问题稿：运动中 stop_move 延迟

**草稿，尚未发送。** 仅包含可公开的技术摘要；不附原始现场日志、设备身份、IP、凭据或本机配置。本稿重点是当前停止链路，不能据此要求操作者重现历史系统停止位移。

## 环境

- LM3；用户从现场版本页提供：L Master/RC `3.1.34+24091315`，DS `2.4.21+24091314`，UI `1.16.0+24080217`；版本尚未再次在线核对。
- Windows，`lebai-sdk-asyncio 0.3.13`，JSON-RPC over WebSocket。
- 现场受限诊断：单次 +Z 3 mm 目标，观测到运动后早停，非连续 VR 验收。
- 当前停止失败不自动调用 `stop_sys`，不自动复位或重试。应用保留 200 ms RPC 等待门限以及停止未确认锁存。

## 已确认的数据

同一客户端捕获点、同一 TCP 流中，唯一 `stop_move` 完整请求到完整回复为 **613.042 ms**。应用记录 SDK await **613.732 ms**，SDK 锁等待 **0.231 ms**。应用约 +203 ms 退出为停止未确认，随后迟到回复不清除 `stop_unverified`。

停止回复待定期间，同连接新发的 24 次只读 RPC 均先完成，完整消息往返 **1.222～11.251 ms**。请求字节得到 TCP ACK 不能证明控制器应用已处理停止。未见选定重传等标志也不能排除无线网络或捕获遗漏。

本次停止后没有新 PVAT 请求。操作者随后确认机械臂完全静止、无异常、未用急停；该后续观察不能证明 200 ms 内停止已确认。现有日志没有控制器的方法入口、减速开始与回复发送内部时刻。

对同一已安装 native SDK 的本机模拟服务器对照中，立即停止回复可在约 1 ms 内通过 SDK await；应用超时、状态验证与迟到锁存符合现有设计。这只排除了所测条件下无条件 600 ms 等待，不证明其它 SDK 负载、网络或控制器行为。

## 请确认的事项

1. RC `3.1.34+24091315` 的 `stop_move` 回复语义是什么：接收请求即返回，等待停止指令投递、等待减速完成，还是等待队列/其它阶段？是否有可提供的处理时序说明？
2. 该版本是否存在与连续 PVAT、队列状态或运动中停止有关的已知约 600 ms 等待？若是，适用条件及现有修复说明是什么？请勿仅以最新版本号替代适用性说明。
3. 不禁用关节的受控停止路径，有无受支持的响应界限和确认方法？`pause_move`、任务停止、`stop_sys` 不能未经说明视为等价替代；项目不会自行更换接口或增大等待门限。
4. 对当前 RC/DS/UI，怎样只读取或下载**已经存在**的控制器诊断日志？希望包含请求接收、方法分发、停止执行、方法返回、回复排队/发送的时间；请说明文件/页面入口、权限、时钟/时区和关联字段。
5. 如果已有日志不足，可否提供控制器端既有网络捕获或同一控制器时钟的最小 trace？如必须改变日志配置、重启服务或重新运动，请先列影响及必须采集的单个变量，现场测试将另行评估与授权。
