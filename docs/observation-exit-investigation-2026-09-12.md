# 观察日志收尾缺失：本机进程隔离实验

## 范围

使用项目实际 `observe_after_stop` 和 `CommissioningRecorder`，数据源仅返回本机构造的 IDLE 样本。没有加载 SDK、建立网络连接或执行真机命令。临时脚本：`artifacts/acceptance/observation-exit-probe.py`，属于不提交的实验产物。

每个情形独立启动一个本机 Python 子进程。只对实验自己创建并持有句柄的子进程执行 kill，不涉及已有服务。日志写入临时目录，检查后自动清理。实验结果是下表，不保留或伪造现场 session。

## 结果

四种情形均正常完成父进程断言，父进程退出码 0；各子进程故意异常退出，退出码均为 1。

| 情形 | 观察汇总 | session_ended | summary.json | 可捕获已 flush 输出 |
|---|---|---|---|---|
| 观察完成后抛普通异常 | 有，interrupted=false | 有 | 有 | 是 |
| 观察任务被一次 asyncio cancel | 有，interrupted=true | 有 | 有 | 是 |
| 对实验子进程执行 kill | 无 | 无 | 无 | 是 |
| 注入 JSONL 写入 OSError | 无 | 无 | 无 | 是 |

写入故障通过替换此子进程内记录器实例的 `_append_batch` 注入，不修改生产文件。它验证真实记录器在写入失败后的行为，不证明现场发生磁盘故障。

## 结论边界

1. **汇总缺失不能唯一证明进程被硬终止。** 写入故障也产生三类收尾同时缺失的现象。
2. 单次协作式任务取消可以正常记录 interrupted，但不能推广为任意 Ctrl+C、重复取消、进程组终止或事件循环崩溃都能收尾。
3. 本机直接读取子进程 stdout，四种情形均捕获了之前 flush 的告警。说明实时输出与会话日志应分别保存；不能依赖末尾汇总来回收告警。
4. 本实验没有复现实验室的 WorkBuddy/Git Bash/`tail -20` 管道，也不证明现场是哪一层丢失输出。`tail -20` 不适合需要即时可见安全告警的执行流程，后续获准测试时应移除。
5. 四种子进程退出码相同，说明单独一个非零退出码也不足以判因；必须一并记录终止发起方、超时/取消原因、实时 stderr 和时间戳。

## 与停止故障的关系

B01 位置反馈明显变化在北京时间 16:01:26～16:01:28；记录截断在约 16:02:25。后来的记录中断不能解释更早的位置变化。两条问题需要分别处理，不因修复输出采集而宣称停止安全。

## 后续本地开发边界

建议先补独立进程观测层：不截断实时 stdout/stderr，保留子进程原始退出码及观察层自身的退出原因，明确运行中/退出/超时但仍运行等状态；不得因等待超时就自动重试运动、自动启停机器人或把“进程退出”当作“机械臂已停止”。

观测层本身可先用本机假命令验证，不需要真机。生产安全停止状态机仍须独立分析、离线验证，当前不恢复运动测试。
