## 2. 本轮最重要的新证据

19 条 SDK PVAT 生命周期记录均为 returned，request_id 连续，无诊断丢弃计数；所有请求都在首次停止请求前返回。`invalidated=false` 对这些已经返回的请求并不矛盾，因为它们返回时尚未发生停止失效化。

这支持“本进程没有在首次停止请求后继续发出新的 PVAT”的判断，但 RPC 返回不等于控制盒内的轨迹已经执行完毕；也不能据此证明不存在未记录的控制盒内部行为或其它控制来源。

更关键的是，287 个观察样本中：

- 控制盒报告的 target_q、target_tcp 各只有一个不同值，target_qd 始终为零。
- target_tcp.x 保持 0.025829141 m；actual_tcp.x 从同一位置附近变化到 0.009545121 m。
- 实际 J2 首尾变化约 +1.02722°，J3 约 +0.60974°。
- 首尾 x 变化 −16.284 mm，与期间最大变化 −16.372 mm 是不同统计口径。

因此需要重点检查停止/系统停机阶段的行为，而非只盯着 VR 输入或新的 IK 目标。目标反馈可能在停机后保持旧值，不能把“目标不变”扩大为“已证明内部驱动指令不变”。

## 3. stop_sys、STOP 与运动 ID 必须分开解释

官方协议将 StopSys 描述为“停止机器人（失能）”；Python 控制文档说明 stop_sys 成功后进入 STOP。因此 stop_sys 是系统级动作，不能当成与 stop_move 完全等价的重复运动停止。来源：[官方协议](https://lebai-robotics.github.io/lebai-proto/)、[Python 控制接口](https://help.lebai.ltd/sdk/python/control.html)。

当前可检验的假设是：stop_move 的本地等待超时后，系统级停止以及重复停止调用与实际位置变化有关。现有日志不能确定失能、制动交接、机械回弹、未完成轨迹或其它机制中哪一项造成位移；尤其不能把这 16 mm 变化认定为正常现象。也不能仅凭返回超时断言控制盒没有收到或执行停止。

同一官方协议明确：GetRunningMotion 在无运动时也可以返回上次 MotionId。因此 running_motion=141 本身不能证明运动还在执行。当前适配器只在 IDLE 分支结合 get_motion_state 清理已完成 ID；STOP/HOLD 下保留 ID 不足以判断其活动状态。

raw STOP 也不能独立证明即时静止：本轮已有 STOP 样本伴随非零速度和连续位置变化。状态与运动学读取非原子，仍应结合连续位置/速度采样，而非单一状态码。

## 4. 六项问题的当前回答

1. **双超时原因**：确认本地等待均达到超时；尚不清楚远端何时完成或为何响应迟到。两轮共四次停止调用，不能当作一次原子停止。已有离线 SDK 实验证明取消本地等待不等于取消远端请求。
2. **samples 为空**：代码在 stop_move 超时后走失败升级分支，未进入正常停止验证采样循环。这解释了空数组，不是本轮观察记录丢失。首次连续观察前仍存在约 844 ms 的停止调用窗口。
3. **running_motion 非零**：需运动状态语义才能判断，不应强求计数器归零，也不能用它单独断言卡住。
4. **位移与 stop_sys 的关系**：时间上相关、接口含系统失能语义，是重点假设；尚未证明因果或具体物理机制。
5. **STOP 是否保证静止**：不足以独立保证，本轮日志已提供反例；仍须连续运动学证据与现场观察。
6. **PVAT returned / invalidated=false**：本轮全部发生在停止前，是一致的结果，不是“停止后仍发送”的证据。轨迹执行是否结束则是另一个问题。

按系统排查流程，已多轮复现后先审视停止架构，不继续通过增加超时或放宽保护安排现场碰运气复测。
