## 本地代码发现

1. `RealLebaiAdapter._call_stop_rpc` 使用 `asyncio.wait_for(..., 0.20)`；超时后调用系统停止，shutdown 又发起停止。Python 等待超时不证明控制盒取消了已收到的请求。现场 SDK 未安装在主机，尚未完成 0.3.13 二进制/源码的取消语义核验。
2. `_read_snapshot` 仅在映射状态为 IDLE 时查询 `get_motion_state`。本次 STOP/HOLD 下的 195 未经过运动状态查询，因此不能写成“195 对应运动仍在运行”。这是诊断信息缺口，不是放行停止的依据。
3. 失败文件没有 `smoke_result`、`smoke_final_state`、`stop_observation_summary`，也无 summary.json。停止失败本身不应被当成这些文件缺失的充分原因：现有代码会尝试观察汇总和 recorder.close。外部终止、文件复制时机、收尾异常尚待终端记录确认。
4. 现有加固的作用是拒绝虚假确认并锁存故障，不保证外部 stop_sys 必定成功。本次没有证据支持放宽 200 ms 超时、取消系统停止兜底或用 STOP+qd=0 直接放行。

## 官方文档与需要确认的问题

- [停止运动](https://help.lebai.ltd/sdk/motion.html)：stop_move 停止运动，但不取消后续新发运动指令。
- [停止手臂](https://help.lebai.ltd/sdk/system.html)：stop_sys 先停止运动，再禁用关节运动。
- [官方 SDK 版本](https://github.com/lebai-robotics/lebai-sdk.rs/releases/tag/v0.3.13)：现场报告使用 0.3.13；主机未安装该包，获取对应源码尚未成功。

STOP 与人工“启动机械臂”恢复 IDLE，与系统停止路径相容，但不能证明禁用关节导致了位置变化。建议把以下问题与原始日志交给乐白技术支持核实，不能靠反复运动试验猜测：

1. PVAT 后 stop_move / stop_sys 的响应时机和正常耗时；响应超时是否仍可能执行。
2. STOPPING→STOP 时，位置保持、关节禁用及制动的实际语义；应读取哪些控制盒日志定位本次变化。
3. SDK asyncio 调用被取消后，底层 RPC 是否仍等待/执行；紧接着重复停止的行为。
4. STOP 状态下 get_running_motion 保留 ID 的语义，以及对应运动状态如何可靠确认。

## 2026-09-12：末帧与日志覆盖边界复核

成功会话 `20260910T072409Z-a74e9db3` 最后一次 pvat_sent 到 stop_requested 为 31 ms；失败会话为 32 ms，两者 horizon 均 80 ms。这是客户端记录的时差，不是控制盒实际执行剩余时间；不能仅凭“停止距离末帧很近”解释一成一败。

失败会话已记录的全部 22 个 PVAT 目标：J2 范围 [-1.5751306122, -1.5681571250] rad，J3 范围 [0.2522004029, 0.2591466573] rad。观察尾样本 J2=-1.5576616163、J3=0.2858956693，已超出这些记录目标的范围；相对末目标分别为 +0.0174689959、+0.0267490120 rad。不能将该反馈变化简单视为向已记录目标正常到位；同样不能只凭目标范围排除动态超调或未记录请求。

**重要诊断缺口：pvat_sent 不是完整的 SDK 发包审计。** `_send_request` 中 move_pvat 返回之后，会检查 `_pump.is_current(request.generation)`；若停止已 invalidate，则直接返回，不写后续 pvat_sent。故没有停止后的 pvat_sent 只能说明没有这类成功登记事件，不能排除停止交界处已经进入 SDK 的请求。需要确认实际 SDK 调用起点、返回/超时及因 generation 作废而未登记的情形。

建议下一项有界改动仅补请求生命周期诊断：SDK 调用前在内存登记 request ID、generation、单调时间与 PVAT 参数；调用返回/超时/取消后登记结果；作废时保留原因；安全动作完成后再写日志，不在 SDK 锁内增加磁盘等待。不调整停止、限位、超时或升级策略。通过本机 fake SDK 验证“在途 PVAT 被作废但确曾调用”仍有证据，再决定是否扩大改动。
