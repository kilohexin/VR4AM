# SDK 二进制的本机停止回复对照

2026-10-10，Asia/Shanghai。仅本机回环实验；没有机器人连接、使用现场配置建立连接或真机动作，暂不推送。

## 问题、设计与范围

上一轮改进了停止取得 SDK 锁的排队。现场抓包仍有完整停止请求至完整回复约 613 ms；只审查源码还不能确定已安装二进制的实际行为。本轮验证更窄的问题：同一份已安装 SDK 在模拟器立即回复时是否仍等待约 600 ms，停止回复待定时其它 RPC 是否能先完成。

`scripts/sdk_loopback_stop_probe.py` 创建自己的 `127.0.0.1` 随机端口 WebSocket JSON-RPC 服务器，再将该唯一已绑定的端口交给 SDK。没有 IP、配置或其它目标参数。模拟服务只允许空参数的 stop_move / get_robot_state / get_running_motion，拒绝运动、夹爪、stop_sys 等方法；不调用发现接口。每轮关闭模拟连接，并通过 SDK 的连接状态/断开等待复核。

固定四种场景：立即成功、请求延迟 100 ms、请求延迟 600 ms、立即错误 -32001；每种三次。两个延迟场景各执行三组状态/当前运动只读调用。模拟值 IDLE/0 只用于协议解码，不能当作物理状态证据。本轮不调用 production adapter/StopRpc，不验证应用 200 ms 停止路径，结果中明确 application_stop_path_exercised=false、hardware_stop_verified=false。

所有调用入口/返回、模拟服务器解析请求及 send 开始/完成均在同一个进程以 perf_counter_ns 记录。send 完成不是抓包的完整回复出现时刻，也不是客户端已经收到了回复；不与旧抓包/控制器时钟直接相减。

## 推断与仍需的证据

这些数据支持：在该二进制、该本机协议与无真实运动负载的条件下，停止 await 不存在每次必需的约 600 ms 固定等待；只读回复也不会普遍被尚未返回的停止调用阻塞。不能排除 SDK 在其它负载/数据/连接条件下的行为差异，不能证明二进制等同于已核对源码。

已结束现场抓包里，约 613 ms 已存在于请求/回复完整消息之间。本机数据进一步削弱通用包装固定 sleep 的解释，但没有提供控制器方法入口、减速执行、回复发送时刻。仍不能区分控制器处理与回复传输，也不能确认物理停稳。

200 ms、stop_unverified、不自动 stop_sys、不复位/重试的策略保持；连续真机 VR 和 Trigger 抓取仍未验收。下一步需要已存在的控制器诊断日志，或另行批准能区分停止语义的单变量现场范围。当前没有发起现场测试或复用旧授权。
