# 第21轮回应：同刻度读取断言修正

## 结论与范围

已核对实验室原始失败输出：读取开始与完成均为 `777059343000000`。原断言错误地要求快速读取必须具有严格正的可测耗时；单调时钟允许连续读取相等。记录与1ms时间刻度一致，但未据此宣称已测得现场硬件时钟分辨率。

本次只改测试和交接文档，不改生产代码、200ms停止等待、故障锁存、采样策略或运动参数。真实停止后约22mm位移仍未解决。

时间源补充：诊断采样器使用适配器传入的 `clock`，适配器默认值是 `time.monotonic_ns`；不应把它直接描述为控制循环注入的 `MonotonicClock` 实例。

## 修正及证据

- 将读取自身的 `started_ns < completed_ns` 改为 `started_ns <= completed_ns`。
- 保留 `stop.started_ns <= read.started_ns` 和 `read.completed_ns < stop.completed_ns`，仍要求停止等待结束前取得读取。
- 保留停止失败锁存、无 `stop_confirmed`、只发送两次停止调用及完整尾部观察等断言。
- 原生时钟用例保留；增加确定性同刻度用例，仅冻结第一组诊断读取的时钟值，首次sample事件提交给诊断记录器后恢复正常时钟，不替换事件循环或停止超时时钟。
- 修正前新用例复现相等值严格小于失败；修正后专项24项通过。

本机验证：全量后端 **821 passed，123.86s，退出码0**。按实验室相同观察器包装执行专项 **24 passed，4.33s**，观察器及子进程退出码均0，`status=EXITED`、`observer_errors=[]`。原始四件产物留存于 `artifacts/acceptance/host-stop-rpc-clock-20260916-001/`。`git diff -- backend/app` 为空，生产代码未改。
