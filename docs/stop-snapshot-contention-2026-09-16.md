# 停止等待期采样：离线阻塞定位

## 已验证的事实

生产适配器 `_stop_verified()` 在 `_sdk_lock` 内等待 `stop_move`；`_read_snapshot()` 也需要该锁。系统停止升级 `_safety_escalate_stop_sys()` 同样使用此锁。因此直接增加一个调用 `_read_snapshot()` 的后台任务，不能保证覆盖停止 RPC 的首轮等待期。

新增 `backend/tests/prototypes/test_stop_snapshot_contention.py` 使用真实适配器、已有 FakeLebaiClient 和事件同步，验证：

1. 假 stop_move 尚未返回时，采样任务已尝试获取锁但不能完成。
2. 释放假停止请求后，停止验证和采样可完成。
3. 取消等待锁的采样任务不会取消停止 RPC。

两种参数场景均通过。测试未加载真机 SDK、未连接设备，未改变生产代码。它是现状特征测试，不是停止故障已修复的回归测试。

## 不能由此推出的结论

- 锁阻塞解释了为什么简单后台采样不能覆盖早期窗口，但不是停止后约22mm位移的根因证据。
- 不能直接移除 SDK 锁：尚未验证 SDK/控制盒并发请求能力、状态读取是否挤占停止请求，以及取消后的资源归属。
- 本测试让假 RPC 在首轮等待期限内返回，不覆盖真实双超时与迟到返回；既有停止事务测试负责那些分支。
- 假 SDK 能并发响应，不代表真 SDK 或控制盒可以。

## 下一步最小实现范围

先设计独立于停止决策的、有界诊断采样通道，并分别验证“可并发读取”和“底层串行阻塞”两种假传输。采样失败必须留下时间戳与错误，不能当作静止；采样不能发送运动/恢复命令，不能改变停止升级期限，取消与断开必须收尾。

在传输并发约束未确认前，不将该通道直接接入真机，不修改200ms升级门槛，不删除 stop_sys，不要求实验室重复原有失败动作。

## 有界采样原型验证结果

离线原型 `diagnostic_sampler.py` 只接收一个读取协程，不持有停止/运动接口。它一次只发起一个读请求，按样本数量限制运行；首次读取超时或异常即停止，不重试。每个成功/超时/错误事件记录单调时钟起止时间，取消与关闭另行记录。它不解释返回值是否代表静止，也不授予运动权限。

新增11项测试覆盖并发读取、共享传输锁阻塞、读取异常、取消采样、取消不响应、禁止复用和非法参数。相关原型及真实适配器控制测试合计 **131 passed**。前三项先运行得到3个预期断言失败；随后取消记录和参数检查先得到7个预期失败，再补齐实现。取消不响应场景在已有清理实现上直接通过，属于补充覆盖，不宣称该项经历失败到通过。

结果与限制：

- 并发假传输：停止任务未完成时可取得样本，采样不会取消该停止任务。
- 串行假传输：读取被锁阻塞后超时，只尝试一次；没有样本就没有静止证据。
- 读取忽略取消：本地等待按清理预算结束，`closed.unresolved=true`，保留任务引用并消费其后续异常；这不是远端取消成功，也不是底层资源已释放。
- 原型依赖协作式异步事件循环。同步阻塞扩展、事件循环卡死和清理期间反复取消尚未验证，不能据此声称进程退出必定有界。
- 目前仅证明采样器自身行为，尚未接入生产适配器；真假SDK并发能力不能互相替代。

后续应先核查实际SDK的请求复用/串行机制，再决定使用同一连接并发读取还是独立只读连接。未得到传输层证据前，暂停扩大离线模型，也不把此原型作为真机修复版本交付。

## 实际 SDK 0.3.13：本机回环验证

已定位官方标签 v0.3.13，提交 `79bc9bba3cc6d710c9c7d3f40f0fe01742911187`。固定版本源码：

- [RPC连接与共享客户端](https://github.com/lebai-robotics/lebai-sdk.rs/blob/79bc9bba3cc6d710c9c7d3f40f0fe01742911187/src/rpc/mod.rs)：普通请求共享 Arc<Client>；可见互斥锁用于订阅读取，不包围普通RPC。普通局域网真实连接默认为3031（仅源码核对，未探测该端口）；SDK默认请求期限1800秒，不是本项目的200ms。
- [系统RPC](https://github.com/lebai-robotics/lebai-sdk.rs/blob/79bc9bba3cc6d710c9c7d3f40f0fe01742911187/src/rpc/system.rs)：状态读取与系统停止都调用共享客户端。
- [锁定依赖](https://github.com/lebai-robotics/lebai-sdk.rs/blob/79bc9bba3cc6d710c9c7d3f40f0fe01742911187/Cargo.lock)：jsonrpsee 0.26.0、cmod 0.4.6。源码构建与实验室安装二进制未作可复现构建比对。

本机原解释器未安装此SDK。用pip向忽略目录 `.tmp/sdk-transport-0.3.13` 隔离安装 Windows cp37-abi3 wheel，不改项目依赖或原解释器包；pip使用本机配置的清华PyPI镜像。导入后SDK自报0.3.13，实际pyd的SHA256为 `ad2a68619b25d627593bd5f13f83f17784e7a2c10aa9615db8bd1b681f9fd03b`，尚未与实验室pyd逐字节核对。

一次性探针 `.tmp/probe_sdk_concurrency.py` 只监听127.0.0.1随机端口，不接受机器人IP、不调用发现设备、不接触控制盒。真实SDK连接本机假WebSocket服务：

1. 实际调用client.stop_move，服务收到请求id=0，但不回响应。
2. 同一client实际调用get_robot_state，服务收到id=1并返回IDLE。
3. 读取已完成且stop任务仍未完成；随后服务回stop响应，stop正常完成。

实测退出码0，`read_completed_before_stop_reply=true`，端点127.0.0.1:50106。探针为临时研究代码，不作为产品或实验室运行脚本。

因此可排除“本次测试的SDK二进制必然把这两种RPC串行化”的假设。不能排除控制盒内部串行、特定方法阻塞、现场安装差异或SDK取消后的未决请求行为；亦不证明停止故障根因。

下一步实现候选应优先考虑**同连接、仅诊断用途的并发读取**，而非先增加第二条控制盒连接。运动命令串行化与现有停止升级策略保持不变；诊断数据不能回写运动快照/清故障，读取超时不能延迟停止，断开时必须保留未解决状态。正式接入前仍需独立设计与回归验证，当前不放行真机复测。
