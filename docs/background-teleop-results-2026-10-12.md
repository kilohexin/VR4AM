# 生产后台控制循环的离线组合验证

日期：2026-10-12，Asia/Shanghai。基线：`36f237dcaed23bb9f94905bb8ef577b983b53e11`。

## 本轮完成

此前的输入、运动和夹爪组合回归主要手动调用控制 tick。本轮启动实际 `RobotControl.start/run`、`teleop_websocket` 会话及其接收、状态发送、诊断发送和清理任务，验证持续收帧和异步停止接管。

生产控制循环使用原 50 Hz 配置，合成输入请求 90 Hz，状态发送使用测试配置的 25 Hz；使用本机真实 `MonotonicClock` 和 `asyncio.sleep`，没有替换 tick、run、时钟或生产停止方法。上述数值是配置和请求节奏，不是测得的实时性能保证。

WebSocket 接口使用内存 JSON 替身，没有 TCP 握手；RealLebaiAdapter 使用真实 `LEBAI` 选解分支和注入的假 SDK。所有关节、TCP、IDLE/MOVING、夹爪数据均为合成数据，没有实际运动或物理抓取。本轮没有修改运行时代码、现场配置或门限。

## 新增覆盖

两种目标策略分别验证以下 5 条路径，共 10 个组合用例：

1. 同一事件循环轮次接受 Grip 释放与重新握住，停止期间保持 HOLD；确认后新帧重新建立锚点，持续握住的旧 Trigger 不发送夹爪，松开后新按压允许发送。
2. 停止输入生产，最后一帧到达原有效期后进入停止流程，随后控制锁定。
3. WebSocket 接收循环发现断线后接管停止，释放会话 owner、发送任务集合和旧最新帧；控制后台任务继续存活。
4. 假停止回复超过原 200 ms RPC 期限，锁存 `stop_unverified`。迟到回复、假原始 IDLE、重 Arm 请求和断线均不能解除锁存或产生新的运动/夹爪指令；原停止事务复用同一个 SDK 请求。
5. 假 SDK 及时返回，但状态持续 MOVING/非零速度，原验证预算结束后锁存 `stop_incomplete`。随后原始 IDLE、重 Arm 和断线不能解除锁存或产生新的控制指令。

另有 1 个测试验证异常清理：内存接收器抛出未知传输错误后，仍退出控制任务、pump、客户端和会话任务，保留原错误。只接受两种预期停止失败的明确错误，不宽泛吞掉其它异常。

## 时间边界核对

首轮断言错误地要求停止生产输入或排入断线标记后立即没有 SDK 调用。原 100 ms 输入有效期内、以及接收循环发现断线前，合法的已排队目标仍可能发送。测试现在以生产关键事件中的 `stop_requested` 为接管边界。

随后还发现不同事件具有相同 `monotonic_ns` 值，不能据此判断发送在停止请求之后。本机当前 Python 运行时的 `time.get_clock_info` 返回：

| 时钟 | 实现 | 报告分辨率 |
| --- | --- | ---: |
| monotonic | GetTickCount64() | 15.625 ms |
| perf_counter | QueryPerformanceCounter() | 100 ns |

测试改为在同一事件循环中同步追加 SDK 入口和关键日志事件，以本地事件顺序判断：`stop_requested` 至 `stop_confirmed` 之间没有新的 PVAT 或夹爪入口。本轮未改变生产时钟，没有将这些本地时钟数据与旧现场抓包或控制器时钟直接相减。

这也说明 nanosecond 字段的单位不等于该时钟的分辨率。当前结果不能作为生产循环实际达到 50 Hz、网络停止延迟或硬件实时性的证明。

## 失败、复审和最终验证

- 首轮 4 失败 / 6 通过；诊断轮 1 失败；调整收帧边界后 2 失败 / 8 通过。复核确认这些断言需要区分有效输入时间、断线发现和相同粒度时间戳，未据此修改生产逻辑。
- 独立审查发现测试清理异常会跳过后续任务退出。首次注入 JSON TypeError 被生产代码正确转成协议错误；改为明确的传输错误后，红回归证明控制任务仍存活。修正测试清理，确保所有退出步骤都会尝试，并最终重抛首个未知错误。
- 最终独立静态复审未发现剩余可操作 P0–P2。审查者未运行测试、联网或访问现场。
- 14 个定向文件 **494 通过**，补充 5 个文件 **120 通过**，共 **614 通过**，JUnit 无失败、错误或跳过。不是后端全集。
