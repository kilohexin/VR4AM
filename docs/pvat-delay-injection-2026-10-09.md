# 发点延迟注入实验与下一处优化选择

2026-10-09，Asia/Shanghai。接续 [分段计时](pvat-stage-timing-2026-10-09.md)。本轮新增离线测试，没有修改生产控制代码，没有机器人连接或推送。

## 实验如何测量

使用既有 FakeLebaiClient 和真实 adapter 调用链；把独立 performance 计数器替换为可控整数，在指定阶段增加 15000000 ns。原安全时钟保持 0。这里的 **15 ms 是人工注入量，不是机器人的实测耗时或预计优化收益**。

四个单变量用例分别注入快照读取、命令锁获取、IK 及人工慢日志回调；新诊断数据正确把增量归入指定阶段，其他三个区间为 0。每例仍只调用一次 IK 和一次 PVAT，没有为获得记录额外读取或运动。

## 两种观察调度的对比

用 asyncio Event 固定实际协程顺序，避免依靠操作系统睡眠碰巧制造竞争：

1. 运动快照持有 SDK 锁，读取暂时等待。
2. 公开状态观察请求排到该锁后面。
3. 运动快照完成并释放锁；公平队列让观察请求先取得锁。
4. 观察仍未结束时，确认 IK 和 PVAT 都没有开始。
5. 观察完成后才开始候选计算和发送。

对照方案把同一份完整观察读取安排在此次发送之后。两种方案都保留两轮 robot_state、estop、kin_data、TCP、claw、running_motion 读取，没有省略安全字段或复用缓存。

| 人工调度 | 命令锁区间内注入量 | 完整读取 | IK / PVAT |
| --- | ---: | ---: | ---: |
| 观察排入运动快照与发送之间 | 15 ms | 2 轮 | 1 / 1 |
| 观察在此次发送完成后执行 | 0 ms | 2 轮 | 1 / 1 |

这验证了可控制的锁排队机制及其分段记录，不能直接说明真实现场观察必须推迟，也不证明优化了整个周期：对照中的观察工作仍然存在，等待转移到了另一个位置。

## 修正日志等待假设

检查并测试实际 CommissioningRecorder：普通 `write_event` 同步把数据加入内存队列，本身没有让出执行，也不在调用处写文件。启动前、启动后两种情况均验证；后台 writer 另用线程批量写盘。

因此，方法是 async 且调用者写了 await，不等于当前调用会等待磁盘。人工慢日志回调只用于验证诊断区间，不代表当前现场 recorder 的实现。正常入队仍有序列化和 CPU 开销；后台 I/O 也可能间接影响调度，这两点没有被排除。

## 选择与实现约束

下一处优化优先研究**观察读取与运动事务的调度协调**，不直接加大 PVAT 时域或删安全读取。生产 `state_sender → control.state_message` 同时承担故障观察和停止完成状态推进，不能把它视为纯 HUD 更新。

实现必须先通过离线故障回归：观察延后有明确上限；停止验证、急停和故障读取不被运动任务持续饿死；IK 超时、取消、状态变化及 Grip 释放后观察能继续执行；等待期间新鲜度检查仍生效。还需比较输入频率与完整周期工作量，不能仅用某一段锁等待消失宣称整体更快。

目前仅确定这一候选方向，尚未修改生产 SDK 锁顺序、观察调度或控制频率。运动停止约 613 ms 回复的问题仍未解决，连续 VR 控制验收仍受阻；不启动新的现场测试。
