# IK 背压冻结与恢复：离线连续实验

日期：2026-10-02。用户要求暂不推送；本次只保存本地改动。

## 实验范围

新增 `backend/tests/robots/test_lebai_backpressure_experiments.py`，使用真实适配器的生产候选选择策略，但客户端全部通过工厂注入 `FakeLebaiClient`。`backend_label="LEBAI"` 用于选中生产算法分支，不代表连接真实设备。测试不调用真实 SDK，不启动服务，不读取现场配置，也不生成现场运动。

这次只增加测试和说明，没有修改运动、背压或停止策略，也没有调整现场参数。

## 模型与初始状态

- 沿用测试配置：25 Hz PVAT 请求、80 ms 预测时域、0.25 rad 跟踪误差门限、0.05 rad 相邻 IK 解步长门限；本实验将测试中的关节速度上限设为 0.05 rad/s，加速度为 0.5 rad/s²。
- 仅第一个关节改变，其余关节保持测试预置值。IK 解由测试显式提供，不使用真实机器人几何模型。
- 通过六次实际泵调用逐步接受 `0.04 / 0.08 / 0.12 / 0.16 / 0.20 / 0.22 rad` 的 IK 解，反馈位置保持 0；不直接改写适配器的接受历史。
- 预热结束：接受的 IK 解是 0.22 rad，最后接受的目标编号是 6，最后发送的 PVAT 关节点只有 0.004 rad，实际反馈仍为 0。三者不能互相代替。
- 随后持续请求 0.26 rad 解。模拟反馈更新为 `q_next = q_actual + gain × v_sent × 0.04 s`，速度反馈为 `gain × v_sent`。
- 该模型只用于检查约束与调度。它没有惯性、负载、控制器插值或正运动学；实际 TCP 在 fake 中不随关节反馈更新。不能据此推算真实 TCP 位移或机器人恢复时间。

## 结果

| 场景 | 观测结果 | 判据 |
|---|---|---|
| `gain=1.0` | 5 次 catch_up 后恢复 advance | 从第一次 catch_up 至首次 advance，相隔 200 ms 的模拟时间 |
| `gain=0.25` | 20 次 catch_up 后恢复 advance | 同一时间定义，相隔 800 ms |
| `gain=0` | 101 个采样点跨 4.000 s，始终 catch_up | 旧目标编号保持 6，发送关节点保持 0.004 rad，无持续 IK 失败故障 |
| 背压期间 IK 跳到其他分支 | 0.50 / 0.45 / 0.40 rad 三次候选均因关节跳变拒绝 | 不发送新的 PVAT；接受历史仍为 0.22 rad / 编号 6 |
| 分支拒绝后恢复连续解 | 新解 0.24 rad 被接受并恢复 advance | 历史更新到当前编号，约束清除 |
| 背压中的 IK 阻塞，同时存在更新的待处理请求 | stop 和 disconnect 两种情况均使在途/待处理目标失效 | 停止边界之后 fake 写入只有 `stop_move`，没有后续 `move_pvat` |
| IK 返回时快照已过期 | 模拟快照老化 341 ms 后拒绝发送 | 泵报告 `robot_state_stale`，没有新的 PVAT |
| 完整控制层 → 适配器 → fake 泵 | 慢反馈下先冻结，后恢复；阶段采样可关联到请求 | 20 次 catch_up，随后 7 次 advance；控制层维持 ACTIVE、无故障，提示最终清除 |

正常和慢反馈两组都在实际反馈达到约 0.01 rad 时恢复：`0.26 - 0.01 = 0.25 rad`，刚好进入跟踪误差门限。catch_up 使用旧解 0.22 rad，不把请求解 0.26 rad写入接受历史。每条发送记录同时检查速度不超过 0.05 rad/s、加速度不超过 0.5 rad/s²。

完整控制层测试使用上一轮新增的 `control_target_sample`：通过输入编号核对每个采样的 `limited_tcp` 等于对应 PVAT 记录的 `requested_tcp`；catch_up 时它与 `target_tcp` 不同。日志中的请求目标与接受目标必须分别读取。

## 两个需要保留的语义边界

### 返回的软约束可能属于前一个泵结果

当前 `command_tcp` 先将新请求放入最新请求泵，再返回已经存在的软约束。实验中首次恢复 advance 的那次调用仍返回 `ik_tracking_lag`；下一个输入调用才返回成功。完整控制层因此多保持一个输入周期的 `last_target`，随后继续推进，界面约束再按现有持续有效时间清除。

所以，单次调用返回跟踪滞后，既不证明新请求没有入队，也不证明新目标已经执行。应结合泵结果、接受编号和遥测分析。这组实验验证了恢复路径，不构成更改异步接口的依据。

### 反馈不前进时没有单独的等待超时

在本实验条件下，只要上一接受解仍位于实际反馈的 0.25 rad 跟踪包络内，连续四秒没有位置进展仍保持软背压，不累计为 `ik_failure_persistent`。从代码也可看到，此分支没有单独的“无进展持续时间”门限。

这是当前策略边界，不等于现场已复现四秒静止、不等于永久等待已获安全认可，也不代表必须增加超时。若要增加无进展检测，应先明确有效反馈时间、最小可测进展和停止响应；直接新增时间门限不能解决既有停止晚返回问题。

## 结论与下一步

本组场景下，现有策略能在反馈进入包络后恢复，也能拒绝分支跳变和停止后的旧请求。没有发现需要立即修改恢复算法的失败用例，因此本轮保留算法与门限。

真实小平移对应大关节需求、控制器为何跟不上、约 609 ms 的 `stop_move` 晚返回仍未解决。下一步继续离线梳理 SDK await 的可观测边界和反馈新鲜度；正常 VR 参数只能先形成候选，不以本实验结果决定现场速度或增益。机械臂上电、连接、动作和新日志采集仍需用户另行明确授权。
