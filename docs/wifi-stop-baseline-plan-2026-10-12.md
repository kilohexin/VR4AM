# 现有 Wi-Fi 下的停止诊断方案

日期：2026-10-12，Asia/Shanghai。准备基线：`75091df555c080fbb8707649ac659f82adf5e45d`。

## 现行约束

用户确认没有条件完成有线连接，也无法取得原厂答复。取消有线网络要求和原厂材料依赖，使用现有 Wi-Fi。历史网址仅作为待现场重新确认的目标，不访问网页或自动探测。

本文件是更新后的方案，**不是新的 SDK 连接或机器人动作授权**。本轮不访问机械臂、不生成可执行批准、不更改现场配置。

## 下一步先完成的软件工作

准备一个仅适用于静止基线的独立诊断入口，固定停止方法为 `stop_move`，不接收任意动作类型。沿用原生产停止事务、独立 QPC 记录和 2 秒只读尾段；保存请求是否复用、SDK await、停止验证、异常与清理证据。

现有通用 `StopAction` 已支持单次停止和尾段，但代码允许在 preflight 未 ready 时发送停止，这是处理运行中/故障中显式停止的既有用途。它**不能直接当成“仅在 IDLE 发一次停止”的专用入口**。静止诊断必须先增加并离线验证以下门禁，再准备真实执行材料：

1. 目标、当前版本和配置散列、单次范围及有效期绑定；保存的批准材料不从本文件自动生成。
2. 用户现场确认目视静止；入口重新只读核对原始 IDLE、完整状态、连接健康、急停与速度等现有条件。未知、运动或条件变化时结束，不从通用 StopAction 的例外绕过。
3. 不启动控制后台输入、PVAT pump 的运动请求、Home、准备位姿或夹爪写入。首次停止 RPC 尚未创建时，门禁拒绝、记录错误、取消或其它异常必须保持机器人写入为零；不得沿通用 `control.stop()` 清理路径意外创建首次请求。只有本次已经创建的停止事务可复用，整个清理过程的独立停止 RPC 总数最多一次，不能自动升级。未知现场运动交由现场观察与应急流程处理。
4. 离线检查及时回复、迟到、错误、仍 MOVING、清理和状态变化，并验证失败后的权限不恢复。单独覆盖停止排队但尚未创建 RPC 时的取消、首次写入前的拒绝/异常零写入，以及首次写入后的收尾复用。既有 `stop_unverified` / `stop_incomplete` 门禁保持。

这些是下一项开发工作；专用入口当前尚未实现，不能宣称已可执行。

## 第一阶段：同一 Wi-Fi 的静止停止基线

软件入口完成后，申请一个新的单次现场范围：当前机械臂已经 IDLE 且用户目视静止，在既有 Wi-Fi 上连接一次，只发送一次 `stop_move`，随后沿原稳定验证与 2 秒只读尾段收尾。没有位移、旋转或夹爪目标。

执行前确认当前完整目标网址、上电/IDLE、工具状态与净空、用户在旁观察并能操作急停、无其它控制客户端。保持实际网络与现场配置，避免把不同软件、网络和状态全部同时改变。

基线优先采用应用 QPC 和结构化日志，不额外要求用户提供控制器日志、安装设备或进行有线抓包。它不包含网络层请求/回复计时，因此不能独立拆分网络与控制器耗时；若后续必须抓包，另列明确范围。

| 基线结果 | 后续决定 |
| --- | --- |
| 当前 IDLE 条件下回复也迟到/失败 | 不进入运动阶段；检查当前连接、方法与应用记录，说明延迟并非只在所选 MOVING 样本中观察到。仍不能直接归因 Wi-Fi。 |
| 回复及时且完整停止验证通过 | 建立当前软件、连接与现场状态的静止基线；允许准备第二阶段材料，不自动执行、不放行持续 VR。 |
| 现场或程序读到运动、异常或状态不确定 | 该次不属于有效静止基线，结束并按现场流程处理；不为了取得基线自动复位、Home、重新启动或重试。 |

“静止基线通过”只检验静止条件下的停止调用和验证链路，不证明运动中的物理停止。

## 第二阶段：保持 Wi-Fi 的单次受限运动对照

第一阶段通过后，另行准备和批准一次原 +Z 3 mm 目标、取得运动证据后早停、2 秒只读尾段的范围，沿用已验证的单次诊断与必要的抓包入口。起始姿态不适合时结束，不扩展成准备位姿。

相比静止基线，关注运动状态、PVAT 与队列条件。两阶段仍不是严格隔离全部变量的实验：运动阶段的输入、控制请求与观察负载不同，Wi-Fi 和控制器负载可能随时间变化。只有配合实际记录才能解释结果。

200 ms 停止 RPC 期限、原低速上限与失败锁存保持；不换成 `stop_sys`、暂停或无回复通知，不增大超时，不用停止 PVAT 发送替代停止确认。运动迟到时仍不进行连续 VR/Trigger 抓取。

## 离线开发继续推进

现场准备期间继续开发静止专用入口和相关门禁，随后处理 VR 输入、目标背压与夹爪组合链路中有明确证据的改进。机器人运动验收与软件开发分别记录，停止故障不会被测试数量或后续 IDLE 覆盖。

本次方案变更只修改文档；独立静态复核指出首次 RPC 前的异常清理可能意外创建请求，已将零写入和取消边界列为专用入口的明确要求。没有新增测试结果，也没有改变生产代码、现场配置或既有冻结证据。当前约 613 ms 的运动停止回复原因仍未知，持续真机 VR 尚未验收。
