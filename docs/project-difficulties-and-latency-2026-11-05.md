# VR机械臂项目：当前难点、延迟原因与解决方案

日期：2026年11月5日。依据本机截至代码`e26addb`的实现、冻结日志及原厂文档编写。本文解释已知问题和后续选择，不代表新真机动作授权。

## 一、当前结论

**项目有继续实现的技术路线，但目前没有完成“真人VR连续控制真机、转腕、抓取搬放”的整链验收。主要瓶颈是实时轨迹计算与执行调度、正常收尾机制、实体夹爪及拍摄路径的集成。不能把问题全部归结为stop_move慢，也不能仅靠提高速度参数解决。**

当前具备网页/VR输入、模型显示、位置控制、PVAT参考生成、工具绑定、故障隔离及若干官方Docker短时运动证据。但这些能力分布于不同历史版本、离线模块和独立诊断入口；不能拼接成“最新真机产品已经可用”的结论。

最新104项定向测试通过，只证明相应软件条件得到检查。最新有限PVAT实际Docker试验仍失败，新版实体入口仍仅预览。没有可信依据给出“完成百分之多少”或保证下次真机一次通过。

| 内容 | 已有证据 | 当前限制 |
| --- | --- | --- |

历史上已经通过的功能保留其价值，但旧模式存在的问题不能通过切回旧入口绕开。例如11月4日旧位姿模式在转腕过程中出现过严重TCP路径偏差，因此该入口仍保持封锁。

## 三、“延迟高、不跟手”的具体原因

### 1. 旧有限小步控制，本身就会产生分段停顿

早期采用“发送一个小目标→等待实际到位→稳定检查→再发下一步”的方式。它适合离散定位，长按或手柄连续移动时则容易表现为动一下、停一下。

把步长或速度调大，可以改变每步的幅度和耗时，但不会消除“每步都等待停稳”的结构。因此，网页位置操作和VR连续跟随应分别设计：网页可以保留位置目标；VR应使用速度/加速度连续的PVAT参考，正常松手通过减速尾段结束。

**状态：原因明确；连续PVAT替代路线已有部分仿真证据，最新真机产品集成未完成。**

### 2. 新规划器计算量过大，且最慢帧不稳定

新版不能只把手柄位置送入IK。每次规划还要检查关节分支、整段TCP路径、速度/加速度，并准备可接管的完整减速尾段。这些检查解决了旧模式只限制关节却未约束末端路径的问题，也增加了计算成本。

已记录的实例：

- 一次20步剖析总耗时约1.379秒，其中尾段规划约0.861秒；尾段构造是该轮主要计算成本。
- 严格旋转转换优化使两组40步模型总耗时约减少10%，但没有消除所有超时。
- 一轮真实工具实时诊断，规划耗时中位数49.39ms、P95约69.35ms、最大95.04ms，而参考周期为80ms。
- 同一帧最多尝试四档不同需求时，会重复求解不同轨迹和尾段。纯模型单档候选提高了新参考比例，但实际跟随仍未完全通过。

当规划迟到，系统不能把过期轨迹继续当作新指令发送，只能暂时消费此前已校验的减速尾段。**连续出现“新参考—减速—再续接”，就会形成明显滞后和速度波动。**

这些数值来自不同试验，不能相加成总延迟，也不是所有操作下的固定耗时。详见[实时主机证据](cartesian-live-host-2026-11-05.md)。

**解决方向：**减少单帧重复需求搜索；将完整尾段计算与实时发送解耦；使用已验证的编译运动学；限制规划工作量，并始终采用最新输入。不能以漏查路径、无限缓存旧目标或刷新旧输入时间换取表面流畅。

### 3. 控制器发送调度也会超出PVAT周期

即使轨迹提前算好，发送仍可能迟到。原厂要求相邻PVAT调用间隔严格小于该包的`t`；超出后可能自动减速。80ms是当前候选的参考周期，相当于每秒12.5个参考端点；它本身不意味着机械臂必须每80ms停一次，连续性还依赖P/V/A和实际发送节拍。[原厂PVAT说明](https://help.lebai.ltd/api/move.html)

当前实际证据：

- 一轮有限程序首包返回60ms，触及本项目原60ms回执期限。
- 显式候选只将首包期限改为80ms后，首包返回检查通过，但第2包尚未进入时，发送间隔已达到119ms，仍不满足原80ms节拍。
- 独立无运动调查中，`rt_sleep(19)`的四次timestamp差为37/30/30/30ms。这说明该环境中不能把请求休眠时间当作实际精确等待时间；尚不足以定位全部开销。
- 直接Lua PVAT接口候选首调用报错，没有取得成功回执；不能声称它已经解决SDK开销。

**解决方向：**先拆分测量发送调用、休眠唤醒、协作任务切换和反馈读取的耗时，再确定稳定的控制器侧发送方法。实时发送任务应只执行必要工作；日志、状态发布和重规划放在独立任务，队列保持有界。直接Lua接口应先查明失败原因，不能失败后自动换接口继续运动。

原厂说明`rt_sleep`是实时调度等待，但这不是本机在所有负载下的硬实时证明。[常用方法](https://help.lebai.ltd/api/common.html)

### 4. 输入到达、计算和提交之间，目标会过期

当前新输入桥默认1:1位移映射；它不等于机械臂能瞬时达到手柄端点。输入、模型计算、通信和实际运动之间都有时间差。

新参考要求输入年龄小于100ms；断流500ms或释放后退出该次输入所有权。一轮真实工具诊断出现17次`stale_input`，最大输入间隔92.70ms。输入间隔本身已接近100ms，再叠加规划和提交时间，就可能被拒绝。

这是“系统确实在收到手柄动作，但机械臂只走一小段、随后减速”的一个已记录机制。它不证明Wi-Fi一定是主因；92.70ms也可能包含输入任务、事件循环或包装程序的调度延迟。

**解决方向：**采集线程独立持续接收，合并尚未处理的旧输入，只规划最新一帧；接收、规划、提交使用可对齐的时间记录。扩大跟随比例会同时放大目标速度和过期时的目标距离，应在发送稳定后调整。

### 5. 轨迹参考落后于手柄目标，是另一种“跟不上”

除了处理延迟，还存在速度/加速度受限后的运动滞后。手柄突然移动较远，机械臂会按允许的速率追赶；动作幅度倍率提高后，这种差距可能更大。

一轮130秒旧输入的离线反事实回放中，目标高度最大滞后仍约168mm。它是**空间差值**，不是168ms延迟；也不能等同于当前真机误差。另一方面，机械臂相对自身参考轨迹只有很小偏差，也不能证明它已经与手柄同步。

**解决方向：**分别测量“手柄到参考”的滞后和“参考到实际TCP”的误差；在执行链稳定后，联合调整跟随带宽、倍率、速度、加速度与工作区。不能只提高一个速度值。

### 6. stop_move约600ms主要影响异常收尾

历史真机记录出现约609ms停止调用返回；最新两轮Docker也出现约631ms。它们说明原200ms回执指标与这些观测不匹配，但**返回时间不是实际机械停止时间，也不是可靠最大值**。另一次调用失败后的停止返回20ms，更说明不能把所有场景简单归成固定600ms。

正常跟随不应每包、每次松手都等待stop_move。应先禁止新目标，再消费已拥有的减速尾段，自然结束；异常时才使用独立停止请求，并分别记录命令回执与实际反馈确认。原厂也说明stop_move不能阻止之后新发的运动指令。[停止接口](https://help.lebai.ltd/sdk/motion.html)

这条路线可以使正常操控不依赖600ms停止回执，但**不能用它忽略异常时的制动和残余位移**。现有停止未确认记录不能直接清除，新的停止等待策略需要单独验证。

## 五、为什么开发进度反复

这里有硬件接口和实时计算问题，也有项目实现与集成问题，不能全部归因于机械臂不够精细或保护太严格。

早期有限小步方案能做定位，却不适合自然连续跟随；旧位姿跟随又出现末端路径偏差，必须重做参考生成。之后增加了完整尾段、身份和反馈核验，计算与调度成本上升。多个独立模块虽有通过记录，最新产品链却尚未贯通，导致“单项测试通过”和“用户仍不能完成抓取”并存。

项目内的60ms/100ms/200ms等数字包含本项目选定的诊断或保护要求，不能一概当作厂商硬性规格。已经观察到不匹配的条件，需要明确区分：是设备/调用确实失败，还是本项目的判据、调度或实现存在问题。修正判据可以是合理工程工作，但必须同时测量实际路径和收尾，不能只改阈值让日志变绿。

现阶段应以一条可重复完成的整链为交付依据，减少并行尝试不同控制策略；记录失败原因、实际收益和下一项验收条件，避免继续累积只有诊断可运行的分支。

## 六、优先拍摄的实施路线

用户现已明确的顺序：**前移约20cm → 抓取 → 抬升30cm → 向右平移50cm → 下降30cm → 同高度放下。** 基座方向对应仍需现场核对。

此前纯几何调查只覆盖“从保存姿态抬升30cm再平移50cm”，没有包含新增的前移20cm和下降30cm，也不是对上述完整新路线的结论。那轮四个水平候选的局部IK均未走完50cm，不等于所有起始布局都无法完成。

建议按以下顺序收敛：

1. **确定稳定的PVAT发送路径。** 查清当前60ms首包、119ms发送间隔及Lua直接调用失败。验收依据是整段连续执行和实际反馈，不能只看回执。
2. **准备可达、可看清的拍摄布局。** 以完整尺寸选起点、物体和落点，生成运动边界和尾段；不默认从旧准备位直接开始，也不默默缩小用户要求。
3. **先完成一轮空载VR整链。** 依次覆盖前移、抬升、侧移、下降、转腕、取消跟随和自然收尾，保留实际剩余位移及故障结果。
4. **加入串行夹爪和轻物体搬放。** 夹爪结果明确、握持已确认后再搬运；失联或未知时不自动开爪。

若使用预先规划的路径、VR只负责触发各段，可以降低在线计算压力、加快做出受控演示，但它应明确称为“VR触发的分段搬运”。**这不等于用户要求的自由连续跟随，不会未经确认替换原目标。** 连续跟随仍需解决在线规划与发送稳定性。

## 七、如何判断后续优化是否真的有效

需要把同一轮操作串起来记录：手柄采样、服务端接收、规划开始/结束、目标提交、控制器接纳、反馈和实际运动。客户端与服务器时钟需对齐或保留误差范围，不能直接相减不同机器的时间戳。

每轮至少比较：

- 首次动作响应及持续跟随延迟的中位数、P95、最大值；必要时用手柄与机械臂同画面录像核对物理响应。
- 实际PVAT发送间隔、规划超时、新参考接纳、过期拒绝及减速退让次数。
- 手柄目标到参考轨迹的误差，以及参考轨迹到实际TCP的误差。
- 松手/断流后的残余位移、到位时间、尾段完成和夹爪保持结果。

目前没有完成新版真实硬件的上述端到端测量，不能承诺最终几十毫秒同步或“像人手一样”无感。普通延迟可以按用户意愿后期优化；但发送断档、转腕路径偏离、未知夹爪和异常停止未确认仍须先处理。

## 八、VR到真机到底延迟多少？是否因为“端侧计算轨迹”？

**现在不能给出一个经过验证的新版VR到真机端到端延迟值。** 最新链路没有完成真实VR连续运动验收，不能拿仿真计算、单次SDK回执或停止返回代替。

| 数值 | 实际测量的对象 | 不代表什么 |
| --- | --- | --- |
| 中位49.39ms、P95约69.35ms、最大95.04ms | 一轮非零工具Docker诊断中的主机规划任务耗时，计时包括线程任务等待/调度 | 不是VR到真机的总延迟，也不是所有场景固定值 |
| 80ms | 当前候选参考段时长和发送节拍约束 | 不是已测得的端到端延迟，也不是每包必须停稳80ms |
| 60ms、119ms | 两轮有限Docker试验的首包返回耗时、下一次发送尝试间隔 | 不是头显网络延迟，也不能直接沿用为真机表现 |
| 约609/631ms | 历史真机/当前部分Docker试验的异常停止调用返回耗时 | 不是正常跟随延迟、实际刹停时间或可靠最大值 |

当前架构分工是：**VR头显采集手柄 → 电脑Python后端生成和校验轨迹 → 原厂控制器执行PVAT → 机械臂运动。** 控制器侧还负责参考/尾段接管和反馈检查。主要IK、参考规划和整段路径/减速尾段计算在电脑后端，不是在VR头显计算全部机械臂轨迹。

如果“端侧”指电脑本地，那么轨迹计算确实是已测到的重要延迟来源；如果指头显，则不准确。问题也不是“只要本地算轨迹就一定慢”，而是当前算法每帧工作量较大、最慢帧超周期，加上通信/调度和退让后形成累积滞后。

总体验可以概念性分为：**输入采样与传输 + 主机排队/规划 + 提交与控制器调度 + 参考运动响应/机械跟踪**。持续跟随时这些环节可能流水重叠，不能直接把不同试验的几个耗时相加。要区分首次动作响应、持续运动相位滞后和松手残余，分别测量。

解决方案是保留本地必要计算，同时减小每帧工作量、采集/规划/发送解耦、控制器侧稳定发送和插补。将整条路径提前算好可降低在线规划压力，但自由VR输入尚未发生，不能全部预计算；大幅预排队还会增加松手残余。用更快的电脑、移到头显或加GPU并不自动解决尾段搜索、任务调度和控制器调用语义。
